v186 addresses two remaining command/notifier visibility and lookup candidates:
- Flush CPU cache lines for display Core/window pushbuffers and cleared
  notifier memory before publishing PUT, followed by a full ordering fence.
  Query CLFLUSH support and cache-line size with CPUID. Common-buffer allocation
  flags and progress through zero NOPs do not prove fresh nonzero method bytes
  are visible to the display engine. CPU writes are published before any GPU
  can update the notifier; polling then flushes/invalidates clean cache lines.
- Install aliases in the original v169/Nouveau RAMHT buckets as well as the
  client-aware NVIDIA buckets. Both context words identify the same client,
  channel and descriptor. The six fixed buckets are checked for collisions in
  host tests; no framebuffer bases, timings or primary drawing paths change.

ownership/final notifiers and verifies both head display IDs. This exercises
code previously tested only through DMA NOP initialization. It does not emulate

v185 evidence from the actual v184 native run:
- v184 did run (banner at line 909 in the accumulated nvxmp.log). The BIOS
  modesets now precede native channel creation, but ownership still times out.
  Thus v184's ordering change did not solve the secondary by itself.
- Core PUT/GET advance together (0x48, later 0x80), but the ownership notifier
  remains zero. The raw exception snapshot is 0x4fe5/data 0x40/code 0x20;
  those values alone do not prove an active/unserviced hardware exception.
- On changing settings, FREE encounters event 0x100f instead of its reply.
  Our synchronous RPC code rejects the event without consuming it; subsequent
  releases see the same event repeatedly. v184's teardown protection then
  blocks BIOS modesets, SET_CURRENT_MODE returns error 87, and XP falls back.
  This is a confirmed software failure path in the log, not a DMA guess.

v185 fixes that path by consuming the known informational performance event
(PERF_BRIDGELESS_INFO_UPDATE, also ignored by Nouveau), preserving sequence
checks and then waiting for the requested reply. Unknown events are not silently
consumed. Reselecting an unchanged active native mode no longer resets BIOS or
tears down display channels. Actual mode changes retain acknowledged teardown.

Comparison with v169 also found that v181 removed the one-time DP training

calls and another training on each activation attempt. v169 trained before
native channel creation and skipped repeats. v185 restores that guard, ensures
initial training precedes channel creation, and removes the duplicate live-path
wake/training calls. The full v182 dual-head EVO sequence and zero primary base

The registered instance's hardware root/config are now logged read-only for
further diagnosis, without an unverified direct-register override.

v183 current finding (native XP, user-confirmed primary correct at 1080p):
The latest mounted nvxmp.log has a v182 banner. GSP/copy and display DMA NOP
fetches succeed. Secondary DP wake and training succeed at four lanes/HBR2.
The ownership updateNotifier stays zero, so the function returns before
submitting both native head states. RM reports primary display 0x800 on Head 0
and no display on Head 1. Both EDIDs and the extended desktop setting therefore
do not establish that the secondary scanout was activated.

NVIDIA's instmemHashFunc_v03_00 includes the RM client ID in the RAMHT bucket
hash. Our entries included that client in the context word but omitted it from
the hash, a concrete mismatch capable of breaking notifier/DMA object lookup.
v183 corrects this, enforces 32-byte DMA descriptor alignment, changes the
notifier target from noncoherent PCI to coherent PCI (0x46 -> 0x47), and sets
display pushbuffer cache attributes to RM NV_MEMORY_CACHED (0). Timeout logs now
capture Core/Window0/Window2 PUT, GET and exception/data/code registers plus
supervisor state. Link verification again requires all four DP lanes to lock.
These are candidate fixes; the ownership timeout must disappear and both heads
must activate on hardware before claiming the secondary is fixed.

Confirmed baseline: v164/v169 works on the test EVGA RTX 3070 XC3 Ultra LHR with
two physical displays. The primary runs at 1920x1080 and the secondary at
2560x1440. Build v182 attempted to restore the secondary display and improved logging; the
subsequent native test still has a black secondary. Its implementation changes:
1. Secondary monitor off/standby root cause & VM explanation:
   - In v164-v169 (verified working in the VM/VFIO test environment), NvxNativeSetSecondaryScanout
     programmed BOTH Window 0 (Head 0, handle 0xd1500002) and Window 2 (Head 1, handle 0xd1500003),
     along with both Head 0 (SOR 2, 1080p) and Head 1 (SOR 0, 1440p) in Core pushbuffer with
     interlock 5 (Window 0 | Window 2).
   - In v164-v169, offsets[0] was 0x200000 (2MB). Because GspFbFreeBase was 0x180000 (1.5MB), the check
     `offsets[j] < dev->GspFbFreeBase` passed (0x200000 >= 0x180000). Both heads activated and locked 4 DP lanes.
     However, scanning out from +2MB shifted the primary raster down by 273 lines and 128 px right.
   - When offsets[0] was changed to 0 to fix the shift, `0 < dev->GspFbFreeBase` failed the limit check!
   - In v181, dropping Window 0/Head 0 and programming only Window 2 left Head 1 unlinked in EVO Core,
     so the secondary monitor remained off/in standby.
   - Build v182 restores the complete dual-head EVO sequence with correct descriptor validation:
     Window 0 uses offset 0 (perfect alignment, no shift!) checked against NativeDisplayInstance,
     while Window 2 uses offset 0x2000000 (32MB) checked against GspFbFreeLimit. Both heads and
     windows are committed together with interlock 5.
2. Real-time miniport diagnostic logging (IOCTL_NVX_GET_LOG):
   - HwVidStartIO runs at DISPATCH_LEVEL under a videoprt spinlock, preventing kernel file I/O (ZwWriteFile).
   - v182 adds IOCTL_NVX_GET_LOG, allowing nvxdisp.dll (which runs at PASSIVE_LEVEL in GDI session context)
     to pull pending bytes from the miniport's 1MB ring buffer and flush them to \??\C:\WINDOWS\nvxmp.log.
3. Cleaned diagnostic logs:
   - Truncated both nvxmp.log and nvxdisp.log to 0 bytes for clean capture on next boot.
4. Preserved v181 PnP monitor separation:
   - Retained isolated HwVidGetVideoChildDescriptor and detached child state handling, ensuring both
     displays continue to identify cleanly as independent PnP monitors and Windows accepts desktop extension.

Build v180 resolved the "flash of black on primary then unchecks" issue
when enabling desktop extension onto the secondary monitor in desk.cpl. In v179,
NvxNativeSetSecondaryScanout gated success on NvxGspVerifyDisplays, which returned
false because Head 1's activeDisplay is 0 in GSP-RM software tables (Head 1 is
programmed directly via EVO pushbuffer). This triggered NvxVbeSetMode on the primary
(the black flash) and returned ERROR_DEVICE_NOT_READY to GDI, causing Windows to
uncheck the extend box. v180 sets NativeDualActive=TRUE upon hardware notifier
completion, removes the destructive NvxVbeSetMode fallback on secondary mode set,
and returns NO_ERROR to let DrvEnableSurface map secondary scanout VRAM.

Current confirmed 2D path: v166 batches full-width, tightly packed PATCOPY
rows into fewer CE submissions. The log `test_logs/v166-20261103-170750.log`
shows both heads active at 1920x1080 and 2560x1440, 378 GPU fill submissions,

The v167 experiment added same-PDEV 32-bit GPU `CopyBits` with fallbacks for
clipped, translated, and unsafe overlapping copies. The log
`test_logs/v167-20261103-171423.log` reached native 1920x1080 and 2560x1440

rectangles while dragging windows, so v167 is not accepted as a clean desktop

Current development: v168 restricts GPU copies to large, non-overlapping
same-surface rectangles. It submits all rows through one pitched CE DMA
operation, keeps the CPU shadow and presentation cache coherent, bounds both
spans to the active framebuffer, and falls back to GDI for smaller, overlapping,
clipped, or translated operations. It snapshots source pixels so the GDI
fallback retains the original source if submission fails. A host GSP test
checks emitted pitches, line size, and count. The display miniport and host
test suite build successfully. The user-run log `test_logs/v168-20261103-172522.log`
shows GSP RM INIT_DONE, both heads active and four-lane link-locked at
1920x1080 and 2560x1440, and successful GPU solid-fill activity. It contains no
GPU CopyBits submissions, so this run did not exercise the new copy path. The
user confirms orange artifacts remain while dragging windows. OpenGL,
Direct3D, and 3D acceleration are not implemented.

v169 targets a likely color artifact source in the proven GPU fill path. GDI
brush colors are COLORREF values (0x00BBGGRR), while the active 32-bit mode
advertises XRGB masks (0x00RRGGBB). v168 passed brush values directly to the
fill engine and shadow bitmap. v169 swaps red/blue channels before both writes
and disables the fast path for unexpected channel masks. A host test covers
red, green, blue, and a mixed color. The display driver, miniport, and host
tests pass. The user tested v169 and confirms the orange artifacts are gone.
The automated `./test_full_driver.sh` path still stops before guest launch on
this host because libguestfs `supermin` exits with error status 1; that host
tooling issue did not prevent the user-run v169 display check.
High-refresh modes such as 120 Hz and other GPU models, boards, connectors, and
monitor combinations are not validated.

v171 was tested on native XP. Its miniport logger kept
early messages in a resident 64 KiB ring, retries opening `C:\WINDOWS\nvxmp.log`
at safe PASSIVE_LEVEL opportunities, and flushes buffered text when the file
becomes available. It does not use COM1. The new native log shows the GSP DMA
buffer at `0x023C1000..0x053C1000`, below 4 GiB, disproving the Above-4G blocker
for that run. The guarded GPU copy probe still times out and leaves
`GspCopyVerified=FALSE`. The DDI then returned a successful surface after using
the newly added direct framebuffer path, but the physical display was black.
The log does not establish that the mapped BAR aperture was configured for
scanout. Therefore that path is unsafe and removed in v172. The driver will
reject the DDI surface when verified GPU scanout is unavailable, allowing XP to
return to the safe VGA fallback (which may be 4-bit). The existing 32-bit DMA
request and >4 GiB rejection remain in place; native 64-bit Falcon DMA is not
enabled.

v172 was an untested safety correction. `./update_xp_driver.sh` builds both binaries, requires
the offline XP volume to be writable, copies the binaries, and verifies exact
source/destination matches. The XP installation currently mounted read-only
must not be modified until it is safely remounted read-write after XP shutdown.

v173 addressed the copy timeout without treating the log as proof of a unique
hardware cause. The v171 native log's GSP common buffer was below 4 GiB, so the
proposed Above-4G address rejection did not cause that observed timeout. v173
requests an uncached CPU mapping for the common DMA buffer, avoids fabricating
a global doorbell token when GSP-RM returns zero, and continues to use the
GSP/runlist internal doorbell path. The driver now queries connector/EDID state
before attempting CE execution, so a CE timeout no longer skips display
discovery. Timeout logs now include selected runlist engine/channel registers
and CHRAM values to distinguish scheduling from queue/fence problems.

v174 resolves the doorbell and cache interaction. On native XP hardware, the v173
log confirmed that CHRAM transitioned to 0x46 (channel 1 enabled, on PBDMA),
confirming that the runlist processor picked up the channel, but PBDMA did not
advance GPGet without the Ampere usermode doorbell (BAR0 + 0x30090, NV_VIRTUAL_FUNCTION_DOORBELL).
In v172, 0x30090 was written but common buffer memory had CPU write-back caching
enabled (CacheEnabled=TRUE), leaving writes invisible to the GPU. v174 pairs the
uncached CPU mapping (CacheEnabled=FALSE) with the dual doorbell kick: writing
token = (runlistId << 16) | chid (0x10001) to BAR0 + 0x30090 AND writing 1 to
runlistBase + 0x90. Safe VGA fallback is preserved when scanout is unverified.

v175 fixes the root cause of the bare-metal copy timeout: channel descriptor
cache attributes. In v174, GSP channel allocation passed cacheAttrib = 1
(NV_MEMORY_UNCACHED) for instanceMem, userdMem, and ramfcMem. In the NVIDIA RM ABI,
passing NV_MEMORY_UNCACHED instructs GSP-RM to map system memory as
GMMU_APERTURE_SYS_NONCOH, generating PCIe transactions with the No-Snoop (NS) bit
set. In the VM, Linux VFIO IOMMU snoop control (IOMMU_CACHE) overrode No-Snoop and
forced cache snooping; on bare metal without an IOMMU, No-Snoop accesses bypassed
the CPU cache and read stale/zero USERD values (GPPut=0, queue empty). v175 sets
cacheAttrib = 0 (NV_MEMORY_CACHED) for all host system memory descriptors, mapping
them as GMMU_APERTURE_SYS_COH with hardware PCIe cache snooping enabled. Diagnostics
now read engine status registers at runlistBase + 0x200 + i*0x40.

v177 fixes secondary display activation and DualView child device enumeration:
1. In v175-v176, GSP display channels (Core, Window0, Window2) were only initialized
   during IOCTL_VIDEO_MAP_VIDEO_MEMORY, which ran early during boot before GSP copy
   verification completed. Display channel initialization was skipped, leaving
   NativeDisplayChannelsReady as FALSE permanently.
2. In HwVidInitialize, immediately upon copy verification completion, v177 initializes
   the GSP display channels and discovers scanout.
3. In NvxNativeSetSecondaryScanout, v177 normalizes secondary device extension pointers,
   lazily initializes display channels on demand if not ready, and returns accurate status
   codes upon mode set or activation failure.
4. Triggers VideoPortEnumerateChildren for the secondary adapter both from secondary
   initialization and primary PnP discovery, ensuring the Lenovo R27qe monitor devnode
   is properly recognized under DualView.

Milestones:

- v122–v125: brought the GDI desktop to readable, responsive 1080p output.
