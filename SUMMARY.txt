Latest hardware result

The archived v33 hardware log is test_logs/v33-20261101-182149.log. VBE exposes

Changes in experimental v30
---------------------------
* Rebased SEC2 bootstrap behavior on matching NVIDIA OpenRM 535.113.01, not the
  unrelated local 615 checkout. Matching source is in /tmp/nvidia-open-535.113.01.
* Implemented GA102 reset preparation, bit-preserving engine reset, Falcon-core
  selection, second scrub wait, and BOOT_0 programming in the Nouveau/OpenRM
  order. The old raw ENGINE writes could clobber unrelated control bits.
* Start SEC2 through CPUCTL_ALIAS when CPUCTL.ALIAS_EN is set, matching OpenRM;
  otherwise start through CPUCTL. Added transition and register diagnostics.
* Added `make -C src_driver package-full`, which builds GSP-enabled v30 into
  dist_full/ and nvx_driver_full.iso without replacing stable v29 in dist/.
* Preserved verified VBE scanout on GSP failure. This is an initialization
  milestone, not yet a full accelerated driver.

v30 hardware result and v31 safety update
-----------------------------------------
v30 made real progress: SEC2 transitioned from HALTED to running, executed the
signed Booter Load code, halted normally, and returned mailbox error 0x91. WPR
was not verified. Windows subsequently blue-screened; serial logging shows its
HwVidResetHw callback was invoked, but the STOP code is not present in COM1.

v31 removes DMA/common-buffer teardown, Falcon writes, and stalls from
HwVidResetHw because VideoPort may invoke it during bugcheck at elevated IRQL.
After a failed GSP bootstrap it explicitly reapplies and verifies the current
VBE mode before the display DLL starts. The new test_full_driver.sh builds,
updates the guest, runs QEMU with reboot disabled, archives the serial log, and
classifies the last GSP stage. Record the visible STOP code if Windows crashes.

v31 hardware result and v32 prerequisite gate
---------------------------------------------
v31 again blue-screened with SYSTEM_SERVICE_EXCEPTION (0x3B). The log proves
the restored VBE mode was accepted, then the crash occurred after the XDDM
display driver queried the current mode and before it mapped video memory. A
partial GSP transition therefore cannot safely return to the display stack.

Matching OpenRM 535 performs board-VBIOS FWSEC/FRTS, reset into RISC-V,
optional scrubber, and only then Booter Load. v32 refuses the unsafe hardware
sequence until FWSEC/FRTS is available. `package-full` is boot-safe;
`package-probe` is the explicitly unsafe reproducer. Run capture_vbios.sh while
the host exposes the GPU PCI ROM so the next implementation can parse and run
the board-specific FWSEC image.

v32 BSOD root cause and v33 correction
--------------------------------------
v32 correctly skipped all GSP hardware operations but still produced 0x3B at
the same point. Package comparison found that dist_full installed an obsolete
10,976-byte nvxdisp.dll, while working v29 used the newer 16,896-byte display
DLL. The failure occurred immediately after mode query, when win32k entered the
display DLL. v33 replaces the obsolete DLL and makes package-full/package-probe
always copy the known-working display DLL from dist/.

v33 hardware result and next milestone
--------------------------------------
v33 is the known-good native-resolution baseline. Preserve its package and Git
tag before changing GPU initialization. The captured sysfs ROM is 157696 bytes,
but BIT's Falcon table pointer is 0x72383 (467843), so that file is only a ROM
prefix and cannot supply FWSEC. The next build must read the complete PROM via
read-only BAR0 NV_PROM_DATA accesses (base 0x300000), parse and bounds-check the
VBIOS FWSEC descriptor, and log it without modifying Falcon state. Only after
that passes should FWSEC/FRTS execution, GSP reset, Booter Load, and RM RPC be
enabled in successive hardware-tested stages.

v34 read-only PROM/FWSEC probe
-----------------------------
v34 adds a bounded parser for chained PCI ROM images, BIT header checksums and
tokens, the Falcon ucode table, and FWSEC v2/v3 descriptors. It reads the full
1MB PROM aperture at BAR0+0x300000 and logs descriptor/image metadata. It does
not reset, DMA to, or start any Falcon. Host sanitizer tests cover a valid v3
descriptor, corrupted checksum, integer bounds, malformed sizes, and the known
truncated sysfs ROM. The next hardware log must show the VBIOS/FWSEC lines while
retaining the verified 1920x1080x32 scanout.

v34 hardware result and v35 diagnostic
--------------------------------------
v34 retained 1920x1080x32 and performed no reset or GSP execution, but the live
PROM parser returned INVALID_ROM (-2). The live aperture likely includes an IFR
prefix before the PCI 55aa image, as handled by OpenRM. v35 logs raw aligned
dwords at the PROM start and candidate PCI/extension/FWSEC offsets so IFR/ROM
location can be implemented from observed data without speculative writes.

v35 hardware result and official firmware verification
-------------------------------------------------------
v35 booted successfully and retained the verified 1920x1080x32 mapping. Its
raw PROM values show PCI ROM images at offsets 0 and 0xfe00, then an NVIDIA
private expansion image at 0x26800 beginning with `NV`; the original parser's
assumption that every expansion image begins with 55aa is therefore incomplete.

The matching official NVIDIA 535.113.01 installer and OpenRM extraction script
were fetched and checksum-verified. The packaged GA10x GSP-RM, SEC2 bootloader,
and Booter Load artifacts are byte-identical to the files already in this
project. The official Booter Unload artifact was added for future teardown.
These generic blobs do not contain the board-specific FWSEC/FRTS data. See
FIRMWARE_PROVENANCE.md for URLs, hashes, and the exact trust boundary.

Changes in v36
--------------
v36 extends the read-only ROM walker with the NVIDIA private ROM signatures
`VN`/0x4e56 and 0xbb77 and private PCI-data signatures `NPDS` and `RGIS`, as
defined by matching OpenRM. A host test reproduces the offsets observed on the
card: base image size 0xfe00, private image at 0x26800, expansion bias 0x16a00,
BIT Falcon pointer 0x72383, and resulting table address 0x88d83. Malformed
private signatures and all previous bounds/checksum cases remain rejected.
No Falcon, SEC2, GSP, or display-engine writes were enabled. The hardware test
should either print a fully bounded FWSEC descriptor or a more specific parser
status while preserving the 1920x1080x32 VBE desktop.

v36 hardware result and changes in v37
--------------------------------------
v36 passed: the live ROM is 0x89000 bytes, its expansion bias is 0x16a00, the
Falcon table is at 0x88d83, and the production FWSEC v3 descriptor parses at
0x43234. Its 0x4ac-byte descriptor contains 0x480 bytes after the 44-byte v3
header, exactly three 384-byte RSA-3K signatures. Its 0xe100-byte IMEM plus
0x800-byte DMEM exactly equals the 0xe900-byte stored image.

v37 validates those relationships, the PKC signature destination, the DMEM
application-interface header and entries, the required DMEM-mapper entry, and
the mapper command-buffer bounds. It logs CRC32 identities for the signature
table and stored image for repeatable read-only comparison. It still performs
no Falcon, SEC2, GSP, or display-engine writes.

v37 hardware result and changes in v38
--------------------------------------
v37 booted safely but the VBE controller exposed only four modes before any
PROM parsing occurred; Windows therefore selected 800x600x32. The FWSEC parser
reached its stricter application-interface validation and returned
BAD_INTERFACE (-6), but v37 did not log which substage failed.

v38 retries VBE controller discovery once when exactly the degraded four-mode
list is observed, after first establishing a verified BIOS mode. It also logs
the FWSEC validation stage and partial interface-header fields even on failure.
This distinguishes a stale VFIO/VBIOS mode list from a driver parser failure.
All GSP/SEC2 hardware writes remain gated.

v38 hardware result and changes in v39
--------------------------------------
v38 booted with all 10 VBE modes and successfully mapped 1920x1080x32. FWSEC
validation reached stage 5: the v1 interface header and both entries were
valid, and the required DMEM-mapper entry was found. The remaining failure is
within mapper bounds, header reads, or command-buffer bounds.

v39 assigns a separate validation stage to each of those remaining checks and
logs the partial mapper offset, signature, version, size, and command buffers.
It also adds an unprivileged guestmount/VFIO test workflow documented in
ROOTLESS_TESTING.md. Firmware execution remains disabled.

v39 hardware result and changes in v40
--------------------------------------
After three host-side launch failures, v39 booted with all 10 modes and mapped
1920x1080x32. FWSEC reached stage 9: mapper `DMAP` v3 size 0x40 and its input
buffer 0x7c0..0x800 are valid. The only rejected value was an unused command
output sentinel at 0x01000000. Matching OpenRM does not consume or validate
that field for FRTS/SB preparation.

v40 treats command output as advisory, completes CRC validation, reads the
GA10x GSP fuse corresponding to FWSEC ucode ID 9, and selects the matching
384-byte RSA signature from the VBIOS table. All actions remain read-only;
FWSEC, FRTS, SEC2, and GSP execution are still gated.

v40 hardware result and changes in v41
--------------------------------------
The third v40 launch attempt passed completely at 1920x1080x32. FWSEC image
CRC32 is 0xbcf1b7e4, signature-table CRC32 is 0x99e7e5ed, ucode-9 GSP fuse raw
value is 3 (version 2), and signature index 2 at ROM offset 0x43560 is selected.

v41 reads the OpenRM layout prerequisite registers without writing them:
physical VRAM size, VGA workspace, MMU lock PLM/range, and current WPR2. It
computes the protected 1MB FRTS placement and logs a dry-run 44-byte FRTS
command against the verified 64-byte input buffer. Firmware execution remains
disabled until this hardware-derived placement is confirmed.

Important corrections
----------------------
Earlier notes incorrectly called EAX=0xffff004f a VBE failure. VBE defines AX;
its low 16 bits are 0x004f, which is success. Earlier code compared all of EAX.
Earlier notes also misidentified 0x616300=0xa00 as framebuffer pitch. Nouveau
uses that register in its head-capabilities setup; it is not pitch evidence.
VBE current mode 3 does not prove 640x480x32 LFB scanout. Assuming that layout
and BAR1+0 was incorrect. A BIOS mode such as 0x112 may instead be 24bpp.

Changes in v29
---------------
* Replaced the hardcoded single-mode fallback with nvx_vbe.c.
* Query VideoPortServicesInt10 and use its allocated BIOS buffer and segment
  registers for controller/mode information. Mapping physical zero had failed
  and produced no mode descriptions in the v28 log.
* Read the BIOS's mode list and valid linear direct-color mode descriptions.
  Report actual width, height, depth, color masks and scanline stride. For VBE3,
  use the linear stride and color-mask fields. Validate framebuffer bounds
  against the PCI BAR1 resource. Do not invent pixel geometry.
* Check AX (low 16 bits of EAX), together with the VideoPort status.
* Establish an initial BIOS graphics mode and verify it with GET_CURRENT_MODE.
  Expose larger modes if the BIOS advertises valid descriptions; perform and
  confirm mode changes. Failed requests keep the previous software state and
  attempt to restore the previous hardware mode.
* Map the actual selected mode's framebuffer physical base and storage size,
  rather than all of BAR1 at offset zero.
* Default builds skip the incomplete GSP bootstrap, so its engine/DMA writes
  cannot interfere with this framebuffer test. A dedicated experimental build
  can enable it with make -C src_driver EXPERIMENTAL_GSP=1.
* Keep v28's checked firmware parsing, corrected 535 ABI and bootstrap tests.

Remaining implementation
-------------------------
The experimental GSP path still needs real SEC2 start diagnostics/correction,
FWSEC-FRTS, full RM event/command handling and post-init exchanges. Hardware
modesetting beyond VBE requires real display objects/commits (NVKMS or Nouveau
port). Hardware acceleration requires memory management and rendering commands,
then the corresponding XDDM/3D interfaces. The current display DLL uses software
framebuffer drawing and is the existing Microsoft-derived binary, not a new
accelerated implementation.
