NVIDIA GA104 XDDM driver — cumulative development summary
Updated: November 4, 2026 (v172 safe native-XP fallback prepared)

Confirmed baseline: v164 works on the test EVGA RTX 3070 XC3 Ultra LHR with
two physical displays. The primary runs at 1920x1080 and the secondary at
2560x1440. The driver initializes NVIDIA GSP, configures both native display
heads, and uploads each desktop framebuffer through the GPU copy engine.

Current confirmed scope: Windows XP x64 XDDM desktop output with native
dual-head scanout and GPU DMA presentation. v165 adds a GPU solid-fill path;
the user confirmed the desktop appears normal during the physical v165 test.
GDI drawing is still mostly software-rendered on the CPU.

Current confirmed 2D path: v166 batches full-width, tightly packed PATCOPY
rows into fewer CE submissions. The log `test_logs/v166-20261103-170750.log`
shows both heads active at 1920x1080 and 2560x1440, 378 GPU fill submissions,
and a full-screen 14.7 MB fill completed as one submission. The user reports
correct resolution with slight desktop artifacts remaining. Batching is
exercised; its performance benefit has not been measured.

The v167 experiment added same-PDEV 32-bit GPU `CopyBits` with fallbacks for
clipped, translated, and unsafe overlapping copies. The log
`test_logs/v167-20261103-171423.log` reached native 1920x1080 and 2560x1440
output and recorded 10,000 GPU copy submissions. The user saw orange
rectangles while dragging windows, so v167 is not accepted as a clean desktop
build.

Current development: v168 restricts GPU copies to large, non-overlapping
same-surface rectangles. It submits all rows through one pitched CE DMA
operation, keeps the CPU shadow and presentation cache coherent, bounds both
spans to the active framebuffer, and falls back to GDI for smaller, overlapping,
clipped, or translated operations. It snapshots source pixels so the GDI
fallback retains the original source if submission fails. A host GSP test
checks emitted pitches, line size, and count. The display miniport and host
test suite build successfully. The user-run log `test_logs/v168-20261103-172522.log`
shows GSP RM INIT_DONE, both heads active and four-lane link-locked at
1920x1080 and 2560x1440, and successful GPU solid-fill activity. It contains no
GPU CopyBits submissions, so this run did not exercise the new copy path. The
user confirms orange artifacts remain while dragging windows. OpenGL,
Direct3D, and 3D acceleration are not implemented.

v169 targets a likely color artifact source in the proven GPU fill path. GDI
brush colors are COLORREF values (0x00BBGGRR), while the active 32-bit mode
advertises XRGB masks (0x00RRGGBB). v168 passed brush values directly to the
fill engine and shadow bitmap. v169 swaps red/blue channels before both writes
and disables the fast path for unexpected channel masks. A host test covers
red, green, blue, and a mixed color. The display driver, miniport, and host
tests pass. The user tested v169 and confirms the orange artifacts are gone.
The automated `./test_full_driver.sh` path still stops before guest launch on
this host because libguestfs `supermin` exits with error status 1; that host
tooling issue did not prevent the user-run v169 display check.
High-refresh modes such as 120 Hz and other GPU models, boards, connectors, and
monitor combinations are not validated.

Native XP troubleshooting: the mounted `nvxdisp.log` records selection of
1920x1080x32 (Mode 9), successful SET_CURRENT_MODE, and successful
VIDEO_MAP_VIDEO_MEMORY, followed by failure of IOCTL_NVX_SCANOUT_GPU_VA with
STATUS_UNSUCCESSFUL. The display driver's old behavior rejected DrvEnableSurface
at that point, which explains XP reverting to VGA. The miniport log ends after
HwVidFindAdapter, but the display log proves later miniport I/O requests were
handled; missing miniport messages alone do not prove HwVidInitialize never ran.
The XP-mounted SYS and DLL hashes matched the corresponding workspace binaries
at inspection time. SetupAPI's v169 entry reflects the recorded install method
and is not sufficient evidence of what the direct-copy update script installed.
The locally prepared v170 ZIP had a stale miniport binary, so compare package
hashes with the script-installed files before using any archive.

v171 was tested on native XP. Its miniport logger kept
early messages in a resident 64 KiB ring, retries opening `C:\WINDOWS\nvxmp.log`
at safe PASSIVE_LEVEL opportunities, and flushes buffered text when the file
becomes available. It does not use COM1. The new native log shows the GSP DMA
buffer at `0x023C1000..0x053C1000`, below 4 GiB, disproving the Above-4G blocker
for that run. The guarded GPU copy probe still times out and leaves
`GspCopyVerified=FALSE`. The DDI then returned a successful surface after using
the newly added direct framebuffer path, but the physical display was black.
The log does not establish that the mapped BAR aperture was configured for
scanout. Therefore that path is unsafe and removed in v172. The driver will
reject the DDI surface when verified GPU scanout is unavailable, allowing XP to
return to the safe VGA fallback (which may be 4-bit). The existing 32-bit DMA
request and >4 GiB rejection remain in place; native 64-bit Falcon DMA is not
enabled.

v172 is a prepared, untested correction. `./update_xp_driver.sh` builds both binaries, requires
the offline XP volume to be writable, copies the binaries, and verifies exact
source/destination matches. The XP installation currently mounted read-only
must not be modified until it is safely remounted read-write after XP shutdown.

Milestones:
- v98: verified GSP-backed GPU copy execution on the RTX 3070.
- v122–v125: brought the GDI desktop to readable, responsive 1080p output.
- v150–v164: implemented native secondary-head scanout and independent
  framebuffers; v164 is the user-confirmed dual-display baseline.
- v165: added the first experimental GPU-rendered solid-fill operation to the
  XDDM `DrvBitBlt` path; physical testing confirmed GPU submissions and a
  normal-looking desktop. Performance benefit beyond this fill operation is
  not yet measured.
- v166: batches tightly packed full-width PATCOPY rows into fewer GPU queue
  submissions; retry restored both displays, with slight artifacts remaining.
- v167: adds a bounded same-surface GPU CopyBits path; first run showed orange
  rectangles and excessive small copies while dragging windows.
- v168: narrows CopyBits to larger non-overlapping rectangles, batches rows
  in one pitched GPU copy submission, and snapshots the source for safe GDI
  fallback. Build and host tests pass; user-run hardware log confirms GSP and
  both native heads, but has zero CopyBits submissions. Orange drag artifacts
  remain; the new copy path has not yet been exercised by the desktop.
- v169: converts COLORREF brush values to XRGB pixels in accelerated solid
  fills. Display and miniport builds plus host tests pass; user confirms the
  orange drag artifacts are gone. The automated host test launcher remains
  blocked by libguestfs `supermin` before QEMU starts.

Validation: the v164 hardware log recorded active Head 0 and Head 1, completed
display-update notifiers, four-lane DisplayPort link locks, 1920x1080 and
2560x1440 surfaces, and successful secondary framebuffer readbacks. See
README.md for compatibility and execution instructions. Firmware origins and
checksums are in FIRMWARE_PROVENANCE.md.
