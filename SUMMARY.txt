NVIDIA GA104 Display Driver — cumulative development summary
Updated: November 9, 2026 (v2.0.0.21: reserve GR context backing)

Hardware OpenGL roadmap — November 8, 2026:
- Use the Mesa-backed architecture from the NullMoth macOS project as a model:
  OS API/front-end shim -> Mesa translation/rendering layer -> NVK/NAK -> a
  platform-specific kernel interface -> NVIDIA GPU. XP needs its own WGL ICD,
  VideoPort/miniport interface, and GSP/RM graphics path; macOS components do
  not plug into XP.
- Priority order: XP x64 first, XP x86 second, Windows 98 SE third. Keep one
  fixed-width user/kernel ABI and architecture-neutral 64-bit GPU virtual
  addresses, with separate user-mode ICD binaries for x64 and x86.
- Stage 1 is Mesa revision/build evaluation. Use the macOS port's Mesa patch
  point as a reference, test a clean upstream NVK/NAK base, and add Mesa as a
  pinned submodule only after the first target build is reproducible.
- Stage 2 is the XP x64 shim and isolated GR bring-up: graphics channel/context,
  memory mappings, validated submit, fence/wait, and fault reporting. First
  gate is one GPU triangle with completed fence and pixel readback, while the
  current display and Copy Engine paths remain stable.
- Stage 3 connects the XP WGL ICD/OpenGL front end through Mesa Zink to NVK/NAK
  if the prototype supports the required interfaces without Linux DRM. Then
  verify NVK/GA104 renderer identity, actual GPU completion, readback pixels,
  and stable dual-head output. Exercise WineD3D only after the ICD works.
- Stage 4 builds/tests the XP x86 ICD against the same ABI. Stage 5 evaluates
  a Win98 ICD and VxD/VMM shim; XP WGL/XDDM/VideoPort pieces are not portable.
- Do not import NullMoth's macOS-specific code as a dependency. Its README
  marks the plugin/translator/kernel components PolyForm Noncommercial and its
  Mesa NVK patch MIT. Reuse the architecture and upstream Mesa instead. Mesa's
  current NVK docs state Linux 6.6 minimum; XP support is unproven and must be
  established by the XP shim/build, not inferred from macOS success.

  * Miniport (`nvxmp32.sys`): Built with `-m32 -march=i686 -D_WIN32_WINNT=0x0501` and runtime stdcall dispatch calling conventions.

  * Explicitly configured `DrvEnableDriver` version return `pded->iDriverVersion = DDI_DRIVER_VERSION_NT4` (`0x00020000`) on 32-bit builds, eliminating the "Display Driver written for a previous version of Windows" warning dialog.
  * Exported undecorated stdcall symbols in `nvxdisp32.def` matching standard Windows XP GDI DDI loader expectations (`DrvEnableDriver`, `DrvEnablePDEV`, `DrvCompletePDEV`, `DrvDisablePDEV`, `DrvGetModes`, etc.).
  * Disentangled startup automated test execution (`run_accel_test.bat` and Run keys) to ensure normal, unhindered boot to interactive desktop prior to benchmark runs.
  * Maintained driver version `2.0.0.3` across miniport, display driver, and INF.

v186 addresses two remaining command/notifier visibility and lookup candidates:
- Flush CPU cache lines for display Core/window pushbuffers and cleared
  notifier memory before publishing PUT, followed by a full ordering fence.
  Query CLFLUSH support and cache-line size with CPUID. Common-buffer allocation
  flags and progress through zero NOPs do not prove fresh nonzero method bytes

  can update the notifier; polling then flushes/invalidates clean cache lines.

  client-aware NVIDIA buckets. Both context words identify the same client,
  channel and descriptor. The six fixed buckets are checked for collisions in

v185 evidence from the actual v184 native run:
- v184 did run (banner at line 909 in the accumulated nvxmp.log). The BIOS
  modesets now precede native channel creation, but ownership still times out.
  Thus v184's ordering change did not solve the secondary by itself.
- Core PUT/GET advance together (0x48, later 0x80), but the ownership notifier
  remains zero. The raw exception snapshot is 0x4fe5/data 0x40/code 0x20;
  those values alone do not prove an active/unserviced hardware exception.
- On changing settings, FREE encounters event 0x100f instead of its reply.
  Our synchronous RPC code rejects the event without consuming it; subsequent
  releases see the same event repeatedly. v184's teardown protection then
  blocks BIOS modesets, SET_CURRENT_MODE returns error 87, and XP falls back.
  This is a confirmed software failure path in the log, not a DMA guess.

v185 fixes that path by consuming the known informational performance event
(PERF_BRIDGELESS_INFO_UPDATE, also ignored by Nouveau), preserving sequence
checks and then waiting for the requested reply. Unknown events are not silently
consumed. Reselecting an unchanged active native mode no longer resets BIOS or
tears down display channels. Actual mode changes retain acknowledged teardown.

Comparison with v169 also found that v181 removed the one-time DP training
guard and repeatedly wakes/powers/trains the transmitter between verified
native channel setup and ownership UPDATE. The v184 log shows duplicate wake
calls and another training on each activation attempt. v169 trained before
native channel creation and skipped repeats. v185 restores that guard, ensures
initial training precedes channel creation, and removes the duplicate live-path
wake/training calls. The full v182 dual-head EVO sequence and zero primary base
are retained; v182's core sequence is substantially the successful v169 one.
The registered instance's hardware root/config are now logged read-only for
further diagnosis, without an unverified direct-register override.

Validation: v185 miniport/display builds and both host suites pass. Regression
tests inject 0x100f before a FREE reply and verify it is consumed; cover unchanged
mode preservation; and verify training is done before channels and not repeated.
Hardware validation remains pending. The latest native run inspected is v184.

v173 addressed the copy timeout without treating the log as proof of a unique

v174 resolves the doorbell and cache interaction. On native XP hardware, the v173
log confirmed that CHRAM transitioned to 0x46 (channel 1 enabled, on PBDMA),
confirming that the runlist processor picked up the channel, but PBDMA did not
advance GPGet without the Ampere usermode doorbell (BAR0 + 0x30090, NV_VIRTUAL_FUNCTION_DOORBELL).
In v172, 0x30090 was written but common buffer memory had CPU write-back caching
enabled (CacheEnabled=TRUE), leaving writes invisible to the GPU. v174 pairs the
uncached CPU mapping (CacheEnabled=FALSE) with the dual doorbell kick: writing
token = (runlistId << 16) | chid (0x10001) to BAR0 + 0x30090 AND writing 1 to
runlistBase + 0x90. Safe VGA fallback is preserved when scanout is unverified.

v175 fixes the root cause of the bare-metal copy timeout: channel descriptor
cache attributes. In v174, GSP channel allocation passed cacheAttrib = 1
(NV_MEMORY_UNCACHED) for instanceMem, userdMem, and ramfcMem. In the NVIDIA RM ABI,
passing NV_MEMORY_UNCACHED instructs GSP-RM to map system memory as
GMMU_APERTURE_SYS_NONCOH, generating PCIe transactions with the No-Snoop (NS) bit
set. In the VM, Linux VFIO IOMMU snoop control (IOMMU_CACHE) overrode No-Snoop and
forced cache snooping; on bare metal without an IOMMU, No-Snoop accesses bypassed
the CPU cache and read stale/zero USERD values (GPPut=0, queue empty). v175 sets
cacheAttrib = 0 (NV_MEMORY_CACHED) for all host system memory descriptors, mapping
them as GMMU_APERTURE_SYS_COH with hardware PCIe cache snooping enabled. Diagnostics
now read engine status registers at runlistBase + 0x200 + i*0x40.

1. **Root Directory Cleanup & Test Directory Consolidation**:
   - All test runners, disk image updaters, and host VFIO management scripts have been moved to `test/`:
     - `test/run_all_tests.sh`: Unified runner for unit tests and 64-bit / 32-bit builds.
     - `test/test_full_driver.sh`: End-to-end integration and verification harness.
     - `test/run_vfio_xp_autoretry.sh` / `test/run_vfio_win98_autoretry.sh`: Auto-retry VM runners with serial monitoring.
     - `test/run_vfio_vm.sh` / `test/run_vfio_vm_win98.sh`: VFIO passthrough QEMU scripts.
     - `test/update_disk_driver_user.sh` / `test/update_win98_driver.sh` / `test/update_xp_driver.sh`: Disk updaters.
     - `test/setup-vfio.sh` / `test/switch-gpu.sh` / `test/dynamic_vfio_switch.sh` / `test/capture_vbios.sh`: Host VFIO tools.
     - `test/reset_test_gpu.sh`: PCI subordinate bridge reset utility.
   - The root directory now contains only core repository assets and build trees.

2. **Windows 98 SE VM Failure Analysis & Fixes**:
   - **Bash Continuation Bug**: `run_vfio_vm_win98.sh` contained `# -no-reboot \` after a line ending with `\`, treating the comment as a line terminator, dropping `-qmp` and `-monitor`, and causing bash to exit with error code 127 under `set -e`.
   - **VMM32 Memory Limit**: Clamped default guest RAM to 1024MB (with 512MB minimum) and injected `MaxPhysPage=40000` (1024MB) and `MaxFileCache=524288` into `SYSTEM.INI` [386Enh] to prevent Windows 98 VMM32 memory manager crashes.
   - **VDD Corruption Fix**: Removed obsolete `*vdd=*vxd` in `SYSTEM.INI` [boot], which caused `LoadFailed (Damaged) = vdd` in `BOOTLOG.TXT`.
   - **Binary Deployment**: Recompiled `nvx.vxd` with the new OpenRM HAL shims and deployed it to `/WINDOWS/SYSTEM/VMM32/nvx.vxd` and `/WINDOWS/SYSTEM/nvx.vxd` in `win98_small.img`.

3. **OpenRM Integration & `nvx_gsp.c` Modularization**:
   - Upstream `open-gpu-kernel-modules` relies on a monolithic 1M-line Linux kernel framework that cannot be linked into 16-bit/32-bit Windows 98 VxDs or Windows XP XDDM miniports without an OS adaptation layer.
   - `src_driver/nvx_openrm_shim.c` and official OpenRM headers (`msgq.c`, `gsp_fw_wpr_meta.h`, `nvtypes.h`) provide hardware register access, doorbell notifications, and Falcon booter execution.
   - Refactoring roadmap for `nvx_gsp.c`: separate monolithic RPC and channel code into clean logical modules (`nvx_ce.c` for 2D Copy Engine acceleration, `nvx_disp_rpc.c` for display scanout, and `nvx_gsp.c` for core bootstrap) using official upstream SDK data structures.
