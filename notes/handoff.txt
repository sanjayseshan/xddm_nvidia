# Phase 2C handoff: XP x64 OpenGL on GA104

Updated November 12, 2026 after hardware run `.31`.

## Current status

The Windows XP x64 package builds and passes the XP import/subsystem audit.
The native Mesa WGL ICD selects Nouveau and creates a Gallium `pipe_screen` and
NVC0 context on the RTX 3070. The `.31` run also completes NVC0 TSC uploads and
context creation without the previous Windows hang. That confirms the earlier
hang was caused by Mesa accepting zero VRAM/GART limits and suffix values from
failed `DRM_NOUVEAU_GEM_PUSHBUF` requests.

Hardware OpenGL is still **not working**. The XP test reports
`[OPENGL_RESULT] FAIL`, `SwapBuffers failed: 183`, a black center pixel, GL
error `0x502`, and Nouveau status `unsupported_count=5 last_operation=00000041`
(`DRM_NOUVEAU_GEM_PUSHBUF`). The DRM shim still rejects nonempty pushbufs; Mesa
therefore does not submit its NVC0 state or draw commands. The bridge status
reports `screens=1 callbacks=0 gpu_batches=0 nvc0_clears=0`. Do not describe
this as accelerated OpenGL or a working cube.

The independent NVX NVC0 clear/semaphore test passes, and 2D fills/copies pass.
GART round trips and a 60 KiB upload to a fresh VA pass. GART freeing currently
quarantines each 2 MiB VA slice to avoid the stale-translation fault; this is a
temporary workaround that consumes VA space.

## Recent fixes

- `.28`: quarantine freed GART VA slices. Verified the standalone 32 KiB
  transfer and 60 KiB fresh-VA upload; retained address-space exhaustion risk.
- `.29`: added detailed pushbuf validation trace. The run still froze during
  the second TSC0 upload; this trace patch was initially missing from the old
  DLL because the test had not rebuilt Mesa.
- `.30`: trace showed `PBK: memory domain limit`; failed pushbuf requests were
  setting Mesa's GART limit to zero. The build first failed because the new
  trace patch was based on the wrong patch state; the patch sequence was fixed.
- `.31`: external patch `0019` preserves suffix/aperture state when the shim
  rejects a pushbuf. The hang is gone and NVC0 context setup completes, but
  real pushbuf submission remains unsupported.

## Next work

1. Implement a validated submission path for the Mesa/Nouveau operations needed
   by GA104 initialization and drawing. Do not pass arbitrary application
   pushbuffers to the miniport. Start by inventorying the exact `.31` push,
   buffer, relocation and method shapes and map each accepted operation to
   kernel-owned objects, address checks, fences and existing CE/GR machinery.
2. Route a bounded Gallium/NVC0 clear through that path and verify GPU readback.
   Then add a shader-backed draw and verify pixels, fence completion and
   presentation. Track `SwapBuffers`/frontbuffer presentation separately from
   rendering; current failure code is 183.
3. Replace GART VA quarantine with correct translation invalidation or a
   reusable page-granular allocator before repeated application workloads.
4. Keep every Mesa customization in `mesa_patches/`; the Mesa submodule should
   be clean outside the build script's temporary patch application. Increment
   the minor version before every hardware test.

## Build and test

Build Mesa with the installed Meson 1.12.1:

```sh
MESON=/tmp/nvx-meson-venv/bin/meson ./test/build_mesa_xp64.sh
```

Full host/build/VFIO run:

```sh
NVX_AUTO_RETRY=1 NVX_GR_CHANNEL_PROBE=1 NVX_GR_PROMOTE_PROBE=1 \
NVX_GR_SUBMISSION_PROBE=1 NVX_BUILD_MESA_ICD=1 \
MESON=/tmp/nvx-meson-venv/bin/meson ./test/test_full_driver.sh
```

`test_full_driver.sh` enforces hardware OpenGL by default and exits nonzero
until `[OPENGL_RESULT] RENDERED` is recorded.
