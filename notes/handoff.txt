## Current status

The latest VFIO run `.129` completed its guest benchmarks and clean shutdown, but
`[OPENGL_RESULT] FAIL`; both same-target triangle readbacks still show zero
green pixels. The explicit scissor reset did not change the result. Full log:
`test_logs/v3.0.0.129-20261113-015132.log`; the latest triangle capture is in
`notes/nouveau-trace-latest.txt`. The run took 100 cube frames in 6.8648 s
(14.6 FPS), and firmware assertion count reached 3 during animation.

The XP x64 Mesa ICD builds and selects Mesa / NV170 (OpenGL 4.3 Compatibility
Profile, Mesa 27.0.0-devel). The run creates a native Nouveau Gallium
`pipe_screen`, allocates its channel and BOs, and submits batches through the
NVX channel. Hardware rendering is still not working: the cube readback is
black and `[OPENGL_RESULT] FAIL`. No cube frame has been proven. `.120` proved
the 24-vertex cube batches complete their release fences, but its one-time
state snapshot actually captured an earlier small QUADS probe. Revision
`.121` fixes the snapshot trigger to require exactly QUADS/24 before recording
the cube state and shader bytes. The corrected snapshot shows plausible cube
vertex fetch, target, viewport, cull, and fill state; the bound shader draw
still writes no colored pixels.
The `.122` snapshot also confirms identity viewport swizzle, depth range 0..1,
all RGBA color-mask bits enabled for target 0, blending disabled, logic op
disabled, and multisampling modifiers disabled. These fixed-function gates do
not explain the black output.
The `.123` programmable GLSL triangle also returns black despite successful
shader compile/link and completed draw fences. This points to a common shader
execution, vertex/raster, or render-target path rather than only the
fixed-function-generated shaders.
Revision `.124` tags draw-state and shader dumps by draw type and captures the
first 3-vertex TRIANGLES draw independently from the 24-vertex cube. The
capture confirms target `0x162e0000`, 64x64 viewport scale/translate, enabled
RGBA writes, vertex input at `0x160900e0`, and stage bindings at
`0x22e9efc0`, `0x22e9f2c0`, and `0x22e9ee80`. The captured input contains
the expected `(-0.8,-0.8)`, `(0.8,-0.8)`, `(0,0.8)` positions. Draw fences
complete, but green readback remains zero. Compare these bound stages and the
viewport/target mapping against Mesa's NVC0 draw setup before changing state.
The trace reports `screens=1 callbacks=0`; callbacks are the unused WGL hybrid
path and do not represent the native Nouveau screen's activity.

The `.102` run confirms readback is not generally returning zeros:
`[MESA_GPU_CLEAR_BACK_READBACK] pixel=32,64,191` and
`[MESA_GPU_CLEAR_BACK_RESULT] PASS`. But multiple draw probes and the cube
still read black with `GL_NO_ERROR`, including the no-depth cube. This narrows
the immediate issue to draw/raster output or draw-target state; it does not yet
prove the draw commands executed correctly. The earlier `.100` cube readback
also preceded its later submission timeout, so that timeout did not explain
the earlier black frame.

The cube test's former "softpipe reference" was invalid: it changed an
environment variable after creating the GL context, then rendered again
through that same context. That cannot switch an existing Mesa screen from
Nouveau to softpipe. The comparison and environment toggle have been removed.
Cube acceptance now relies on actual colored pixel count, visible color faces,
bounding box, GL error state, and newly submitted GPU batches. The no-depth
check requires at least 2,000 colored pixels and new GPU batches, so two black
frames cannot pass. In both `.101` and `.102`, depth and no-depth cases fail at
0 colored pixels.
