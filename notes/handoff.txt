Updated November 11, 2026, after the ABI 18 GART BO test on the RTX 3070.

## Verified XP GART BO path (November 11, 2026)

Implemented the 230 MiB GART VA window `0x11a00000..0x1fffffff` in
`src_driver/nvx_gr_context.[ch]` and wired it through the miniport. It uses 115
2 MiB slices, each with a 512-entry 4 KiB page table in a VideoPort common
buffer. The PTE pages are installed in the existing PD0, and map/unmap perform
an RM VASpace TLB invalidate. GART BOs use common-buffer backing; a backing
whose mapping or teardown cannot be confirmed is retained. ABI 18 adds the
client session token to free/upload/download requests so GART BO operations
must match the owning active session.

Host checks pass with `make -C src_driver check`; both `nvxmp.sys` and
`nvxmp32.sys` build. Full RTX 3070 test:
`../test_logs/v3.0.0.8-20261111-203107.log`. The guest allocated GART BO id 2
at `0x11a00000`, uploaded 1024 bytes, downloaded them through the GPU copy
engine, matched every byte, and unmapped/freed the allocation:
`[NVX_GART_BUFFER_ROUNDTRIP_RESULT] PASS`. Caps report 241172480 bytes of GART.
The same run reports `[NVX_3D_RESULT] PASS` and existing GR/2D checks pass.
One startup firmware assertion remains; no MMU fault was logged.

This verifies the bounded XP allocation, GPU mapping, transfer, readback and
free path. It does not verify Mesa/Nouveau GEM use or OpenGL rendering: the
renderer remains `[OPENGL_RESULT] SOFTWARE`, because Mesa screen creation
still stops at `NOUVEAU_CHANNEL_ALLOC` (`ENOSYS`). Next implement and validate
an RM-managed Nouveau channel/client/object lifecycle, pushbuffer submission,
and fence completion; then run Nouveau screen initialization and prove a
Gallium-rendered framebuffer on hardware. Keep Mesa customizations under
`mesa_patches/` and do not modify the Mesa submodule.

## Exact GA104 Nouveau screen bootstrap contract (source audit)

The next transport milestone must satisfy the initialization sequence in the
pinned Mesa sources, not just return success for `DRM_NOUVEAU_CHANNEL_ALLOC`.
`nouveau_screen_init()` creates a FIFO channel, Nouveau client, and a 512 KiB
mapped pushbuffer, then performs a zero-dword pushbuf kick. `nvc0_screen_create()`
allocates/maps a 4 KiB GART fence BO, selects classes, emits setup methods, and
kicks them before it returns a usable screen.

For chipset `0x170` (GA104), `nvc0_screen.c` skips the legacy SW object because
the chipset is at least `0x140`. The minimum screen object set is therefore:

* One M2MF class selected from NVF0 P2MF (`0xa140`), NVE4 P2MF (`0xa040`), or
  NVC0 M2MF (`0x9039`) using `nouveau_object_mclass()`.
* Ampere copy class (`AMPERE_DMA_COPY_B`, `0xc7b5`), selected ahead of older
  copy classes for this chipset.
* NVC0 2D class (`0x902d`).
* GA102 3D class (`0xc797`), selected ahead of TU102 and earlier classes.

The 2D and 3D objects are followed by method streams that set object bindings,
2D state, 3D raster/compression/multisample state, internal buffers, and
shader/constant-buffer addresses. A channel implementation must return class
enumeration consistent with the classes actually bound, and its submission
path must validate and execute these setup batches before claiming the screen
is initialized. The current private C56F/C797 probe channel and fixed clear
escape do not provide this client channel contract. Do not fake the kernel
channel handle or return a successful channel allocation before the matching
owned submission/fence path is live.

Source evidence: `mesa/src/gallium/drivers/nouveau/nouveau_screen.c`
(`nouveau_screen_init()`); `mesa/src/gallium/drivers/nouveau/nvc0/nvc0_screen.c`
(`nvc0_screen_create()`); `mesa/src/gallium/winsys/nouveau/drm/nouveau.c`
(`nouveau_object_channel_new()`, `nouveau_object_mclass()`, and
`nouveau_pushbuf_kick()`). This audit changes no runtime behavior.

## Nouveau screen bootstrap boundary audit (November 11, 2026)

Followed initialization beyond the first unsupported ioctl to avoid treating
`DRM_NOUVEAU_CHANNEL_ALLOC` as the only missing piece. In
`mesa/src/gallium/winsys/nouveau/drm/nouveau.c`, Nouveau channel creation expects
an engine channel plus pushbuffer domain and notifier metadata. In
`mesa/src/gallium/drivers/nouveau/nvc0/nvc0_screen.c`, `nvc0_screen_create()`
then initializes the common screen/pushbuffer, allocates and maps a fence BO,
creates SW, M2MF, copy, 2D, and C797 objects, emits object bindings and setup
methods, and submits those methods before returning a `pipe_screen`.
`nouveau_pushbuf_new()` itself issues a zero-dword `DRM_NOUVEAU_GEM_PUSHBUF`
kick; normal setup and rendering kicks pass user arrays of BO references,
relocations, and push dwords, then depend on kernel-updated suffix and presumed
BO state. The XP shim currently supports limited metadata and GEM BO operations
only. Its NVX batch path is validation-only, and its native submit path accepts
one fixed clear profile. Thus implementing a channel-allocation response alone
would only move initialization to the next unsupported operation.

Next implementation gate: add a miniport-owned client submission contract that
can safely cover channel/session lifetime, required object bindings, BO
references, the NVC0 screen-init method stream, ordered submission, and fence
completion. Do not return a successful Nouveau channel until the matching
session and submit operations work end to end; do not expose `nvc0_screen_create`
to WGL until its initialization kick can complete. The present single private
C56F test channel and fixed-profile clear do not satisfy this contract. Any
Mesa-side changes remain external under `mesa_patches/`; keep the Mesa
submodule clean. This source audit does not change runtime behavior: latest
hardware evidence still reports `[OPENGL_RESULT] SOFTWARE` because the channel
request returns `ENOSYS`.

## Client ownership requirement for a Nouveau channel (November 11, 2026)

The existing `ClientToken` is generated in user mode and supplied on each
buffer allocation. The miniport stores it and uses equality checks to group
buffers and validate batch references, but does not issue the token or bind it
to a kernel-observed client/session. It is therefore an accounting key, not an
authorization boundary. A new channel/session contract must establish kernel-
owned lifetime and caller identity before accepting Nouveau buffer references
or commands. The current miniport also has one shared C56F channel and shared
GR state, so a logical token alone cannot isolate multiple WGL clients. Do not
promote this token or the shared channel into a generic DRM channel.

## Persistent Nouveau BO mappings and pushbuffer visibility (November 11, 2026)

The XP BO adapter stages maps in a CPU shadow and uploads writes on unmap.
Mesa's legacy Nouveau winsys keeps pushbuffer BOs mapped while submitting them,
so relying on unmap would leave the latest command stream only in system
memory. Added `NvxNouveauBoFlush()` and an XP `NvxXf86DrmFlushBuffer()` hook;
the external Mesa patch flushes referenced mapped BOs before a future
`GEM_PUSHBUF` call. Unmapped buffers are a successful no-op. Mock tests verify
the upload occurs while the mapping stays open and that the shim can flush a
persistent mapping.

## Windows replacement for `xf86drm` (November 11, 2026)

Yes: Mesa's libdrm calls can be adapted to Windows interfaces, and this tree
already has the first part of that adapter in `mesa_patches/nvx_xf86drm.c` and
`mesa_patches/xp_include/xf86drm.h`. On XP the transport is the display driver's
`ExtEscape` path (`nvx_winsys_win32.c`), not a POSIX file descriptor. The shim
uses a process-local compatibility token where Mesa expects an `fd`, and
translates calls into versioned NVX escape requests.

The working mappings are device/version discovery to NVX capability and PCI
identity queries; Nouveau GEM allocation/info/close to NVX buffer allocation,
metadata, and free; CPU_PREP to NVX fence waits; and BO map/unmap to bounded
download/upload operations with a CPU shadow copy. These are operation-specific
translations, not implementations of Linux DRM. The original libdrm header has
many unrelated APIs; the XP header intentionally declares only the subset
needed by Mesa's Nouveau DRM winsys.

There is no Windows API call that directly provides DRM channel allocation,
NVIF object creation, relocatable GEM push submission, PRIME sharing, or DRM
ioctls. Those need matching miniport-owned NVX operations and explicit lifetime,
validation, and synchronization rules. In particular, pretending the current
private GSP channel is a DRM channel or returning success from `GEM_PUSHBUF`
would not make Mesa's submission contract work. `ExtEscape` can carry a new
versioned interface, but the kernel side still has to implement it.

The NVC0 batch preflight is being strengthened independently: it now checks
known direct GPU address method pairs against referenced client-owned buffers.
It remains validation-only; it does not submit batches, and a complete
C797 method allowlist is still required before the kernel may execute them.

## Nouveau channel and pushbuffer boundary audit (November 11, 2026)

### Exact Gallium first-call contract (source checked November 11, 2026)

For GA104, Nouveau's `nouveau_screen_init()` creates a
`NOUVEAU_FIFO_CHANNEL_CLASS` object with `nve0_fifo.engine = 0x30`
(`NOUVEAU_FIFO_ENGINE_GR`). `nouveau_object_channel_new()` sends a
`drm_nouveau_channel_alloc` request (32 bytes): framebuffer and TT context-DMA
handles are request inputs; channel ID, pushbuffer domains, notifier handle,
and up to eight subchannel class/handle pairs are response fields. The returned
channel ID becomes the object handle used by all later object operations.

Before any NVC0 screen setup methods, `nouveau_pushbuf_new()` sends a
zero-push `DRM_NOUVEAU_GEM_PUSHBUF` with only that channel ID and consumes the
returned `suffix0`/`suffix1`. It then allocates a 512 KiB CPU-side pushbuffer.
`nvc0_screen_create()` allocates/maps a fence BO, queries channel classes with
NVIF `SCLASS`, creates SW/M2MF/COPY/2D/C797 objects with NVIF `NEW`, and queues
initialization methods referencing GPU BO addresses. Normal GEM push submits
user pointer arrays for BO references, relocations, and push dwords; Nouveau
consumes kernel-updated BO presumed domains and push suffix state after each
kick. A channel response by itself is therefore not a useful milestone.

Acceptance gate for a first channel vertical slice: real RM channel ownership
for the session; correctly initialized response metadata; the zero-push kick
and suffix update; accurate `SCLASS` results; safe object create/destroy; and
one known screen-init method batch copied into kernel memory, validated, emitted
on the scheduled channel, and fenced. Only then let WGL retain the NVC0 screen.
The following gate must cover normal NVC0 resource and draw submissions before
claiming accelerated OpenGL. The existing miniport fixed-profile clear cannot
meet either gate.

The existing GR path is a single miniport-owned GSP-RM channel. The diagnostic
GR setup allocates channel handle `0xc56f0002`, stores its 512-entry GPFIFO and
push memory in the miniport's private DMA scratch allocation, and serializes
the native clear submitter with a global lock. `NvxGspSubmitNvc0NativeClear()`
adds a kernel-owned C797 object bind, accepts exactly the 28-dword clear
profile, then appends idle and a report semaphore. It does not expose channel
memory or a kick operation to Mesa.

Gallium Nouveau's `nouveau_screen_init()` requests a FIFO channel before it
creates the client pushbuffer. `nouveau_pushbuf_new()` immediately sends a
zero-push `DRM_NOUVEAU_GEM_PUSHBUF`; normal kicks later send user pointers to BO,
relocation, and push arrays, and expect kernel-updated BO domains and suffix
state. `nouveau_object_new()` also uses the returned channel for NVIF objects
and channel teardown. Therefore returning the existing RM handle as if it
were a libdrm channel would mismatch lifetime, ownership, and submission
semantics.

A viable bridge needs a client-token-owned logical session, operation-specific
NVIF object handling, bounded copying/serialization of the GEM push arrays,
the NVC0 `PUSH_REF` BO set, kernel validation of C797 methods and every direct
GPU address, actual emission on the private GPFIFO, and completion/fence
results. The current batch IOCTL only validates framing/BO ownership; the
native clear IOCTL only submits its exact profile. Neither is a generic
pushbuffer submission service. Do not report channel allocation success
until this session can reach a validated, fenced batch execution path.

## NVX batch BO references (ABI 13, current work)

ABI 13 extends the bounded batch header with explicit BO reference count and
adds fixed-width `NVX_3D_BUFFER_REFERENCE` entries. The miniport's existing
validation-only batch IOCTL now validates unique referenced BO IDs against the
client token and checks reference access bits; relocation records must also be
covered by a matching reference. `NvxNouveauPushbufReference()` builds these
records, and relocation registration merges access for the same BO. NVC0's
Mesa path was source-audited: it uses `PUSH_REF` and direct GPU addresses in
method dwords, with no `PUSH_RELOC` calls in the NVC0 driver directory. The
references are therefore relevant, but kernel validation must still check the
C797 methods and prove each direct address belongs to a referenced BO.

## Performance and architecture

The current bridge CPU-rasterizes general OpenGL through Mesa softpipe, recognizes a limited class of flat-color triangle batches, submits those batches to C797, waits synchronously for fences, then reads tiled GPU pixels back to update the software framebuffer. A 12-triangle cube frame commonly spends about 31–78 ms in draw submission/waits and 15–47 ms in readback. The earlier depth-off diagnostic reached 21.3 FPS. Its depth modes did not actually select a Zeta target, so do not treat them as depth-attached performance. These are prototype-bridge measurements, not native-Gallium performance. The 63 FPS run in `212323.log` had `gpu_batches=0` and was software-only.

Substantial speedup requires batching work, reducing or removing tiled readback, rendering into GPU-owned resources, asynchronous submission, and an efficient presentation path. The current bridge waits for each draw and copies pixels back after it; that serializes CPU and GPU and makes each frame pay for submission, synchronization, and readback. The experiment removing `NVC797_WAIT_FOR_IDLE` from runtime draws stalled sooner and was reverted, so asynchronous execution needs explicit in-flight resource and fence ownership rather than simply deleting the wait. Temporary report-semaphore checkpoints now bracket early common state, viewport clip setup, color-target binding, depth/state setup, draw completion, and idle completion. They add command work and should be removed after the targeted method bisection.

The CE copy/fill/upload wrappers now serialize shared scratch access against GR submissions. The user-triangle path holds that lock across target prefill, vertex staging, GR submission, and readback, using locked CE helpers for nested calls. Host/mock checks, the XP x64 miniport build, package audit, and real-hardware boot pass with this change. It did not eliminate the intermittent GR stall.

## Recommended plan for full OpenGL acceleration with reasonable performance

The recommended route is a feasibility-first port of Mesa's Nouveau NVC0 Gallium backend for GA104. Reuse its generation-specific state and shader compiler/codegen where the pinned Mesa revision permits; do not assume its Linux DRM winsys, build system, or synchronization layer can run on XP. First inventory those dependencies and build the reusable compiler pieces with the project's XP toolchain. If NVC0's screen/context and command submission are too coupled to libdrm/Linux, retain its reusable compiler and hardware definitions while writing the smaller NVX Gallium screen/context and XP winsys around the existing miniport. This avoids both extremes: attempting to port Linux kernel interfaces wholesale and writing a new shader compiler from scratch. Keep every Mesa change as reviewed patch files under `../mesa_patches/`; do not modify the Mesa submodule checkout directly.

## NullMoth-inspired port strategy for XP

Adopt NullMoth's architectural principle: keep Mesa/NVIDIA's real GPU backend and replace the operating-system service boundary. Do not try to link its macOS code or Linux DRM winsys into this XP driver. NullMoth's documented stack is Apple's OpenGL-to-Metal path, its Metal plugin and Metal-shader translator, Mesa NVK/NAK, and NVIDIA's open kernel modules with an XNU OS layer in place of Linux's. Its OpenGL support comes through Apple's GL-on-Metal interface. That is a useful example of backend reuse plus an OS port, not a ready-made XP OpenGL driver.

For this project, use the native Mesa OpenGL/Gallium route first: make Mesa WGL create an NVX Gallium `pipe_screen`/`pipe_context`, and port the Nouveau NVC0 backend's GA104 shader compilation, state emission, and resource/layout logic as far as dependencies permit. Replace Nouveau's Linux DRM/libdrm winsys boundary with an XP winsys that calls the existing miniport through a small, versioned, validated ABI. That ABI should expose resource handles and mappings, GPU virtual-address ownership, uploads, batched command submission, fences, and presentation; it must not expose arbitrary user pushbuffers. Keep XP DDI/ICD integration and compatibility changes in patch files under `../mesa_patches/`, with the Mesa submodule pinned and clean.

The present `nvx_wgl_bridge.c` is not that port: it hooks softpipe after software processing, filters constant-color triangles/quads, repacks a custom vertex format, submits custom C797 work, waits synchronously, and reads the result back. It is useful evidence that the miniport can execute bounded GPU commands, but it is not a substitute for the NVC0 Gallium backend. Retire it from the normal rendering path as the native screen gains capabilities; keep only small isolated probes for kernel/command regression coverage.

Do not choose NVK plus Zink solely because NullMoth uses NVK. That stack targets Vulkan/Metal on macOS and adds an OpenGL-to-Vulkan route; XP has neither Apple's Metal interface nor a ready Linux DRM Vulkan winsys. Reconsider NVK/Zink only if the pinned Mesa revision and XP WGL integration make the reused NAK compiler/backend materially easier to adapt than NVC0. The success criterion is high reuse of GPU-specific code and a narrow, explicit OS shim boundary, not a literal 99-percent source-count promise; quantify reusable files and remaining Linux dependencies in the feasibility audit before committing to the port direction.

Implementation gates for this approach:

1. **Backend map:** record the Mesa submodule commit (`cc2dcf9abdc6afc093e85d48e4cfa34eed60a01e` at this handoff), locate NVC0 screen/context, compiler, resource, and winsys dependencies, and classify each as reusable, shimmed, or replaced. Preserve the Mesa submodule; carry all deltas as ordered patch files.
2. **XP winsys contract:** specify resource ownership, GPUVA, memory visibility, command batching, fence semantics, reset/error handling, and present. Keep bounds/lifetimes validated in the miniport; make the user/kernel structures x64-safe and versioned.
3. **Native screen bring-up:** register NVX with Mesa WGL and prove screen/context lifecycle without softpipe callbacks. Report only caps whose implementation exists.
4. **Resources and first draw:** support persistent buffers and GPU render/depth targets, upload/map, clear/copy, a compiled vertex/fragment shader, triangle draw, fences, and bounded readback comparison. This gate must execute the NVC0-derived shader path, not the custom softpipe triangle bridge.
5. **Presentation and useful GL:** render the frame into GPU-owned images and present with one GPU copy/blit to an XP-displayable surface; then add target-app-required depth/stencil, textures, blending, and state. Keep CPU readback out of normal frames.
6. **XP and performance acceptance:** audit DLL imports/CRT/ABI on the XP image and run the target workload for 1,000 frames at 632x453: correct reference output, all supported frames on GPU, no fallback/freeze/channel timeout, no new firmware assertions/MMU faults, and at least 30 FPS with frame-time percentiles recorded.

Replace the DRM winsys boundary with a Windows adapter around the project miniport; enumerate the BO/bufctx/pushbuf/fence APIs NVC0 consumes and isolate which helpers can remain source-identical. 2. **Define a safe, efficient user/kernel contract.** Add persistent GPU resource handles, bounds and usage validation, explicit GPU VA ownership, batched command submission, asynchronous fence completion, and resource retirement/reset rules. 3. **Stabilize the existing hardware contract in parallel.** Isolate the current C797 depth/stall failure with clean, non-busy resources; fix the depth-enabled reference mismatch; remove temporary checkpoints once the first failing method is identified. 4. **Build a real Gallium screen/context and GPU-owned resources.** Register the NVX driver in the pinned Mesa build and route WGL context creation to it. Implement lifecycle, truthful caps, buffers, textures, render/depth surfaces, map/transfer, clear/copy, and fences. Ensure ordinary draws no longer pass through softpipe. Keep softpipe available as a deliberate fallback for unsupported contexts/features.
5. **Bring up a shader-backed pipeline and presentation.** Reuse NVC0 lowering/codegen if compatible with the pinned Mesa IR; otherwise choose the shader IR already supported there. ## What it would take to convert this into a Gallium driver

This is a multi-stage driver project, not a small change to the current callback. The current hook observes softpipe after software processing and forwards a narrow subset of its results. A real Gallium driver must own the Gallium interfaces and execute rendering on the GPU without using softpipe as the renderer or copying every result back into its tiles.

1. **Add a real Gallium driver and WGL integration.** Implement a GA104 `pipe_screen` and `pipe_context`, register them in the pinned Mesa build, and make the XP WGL loader create this screen directly. Provide capability queries, context creation/destruction, state objects, resource/surface/view objects, queries, fences, flush, and synchronization. Preserve Mesa customizations as reviewed patch files in `../mesa_patches/`; do not edit the Mesa submodule in place.
2. **Build GPU resource management.** Define resource creation, destruction, reference counting, map/unmap, transfer and staging paths, CPU/GPU visibility, layouts and tiling, render-target allocation, and residency rules. Add robust bounds and lifetime validation. Start with a small supported set of formats and dimensions, then grow it based on tested needs.
3. **Translate Gallium state and draw calls.** Implement clear, copy, `draw_vbo`, flush, and the state needed by the first target applications: framebuffer bindings, viewport/scissor, vertex elements and buffers, primitive topology, rasterizer, blend, depth/stencil, and constants. Convert Gallium vertex/index data into GPU resources and submit batches; remove extraction of post-softpipe constant-color triangles.
4. **Provide a real shader path.** Choose and pin a Mesa IR path (likely NIR for new driver work, subject to compatibility with the XP-era Mesa revision), then implement shader lowering, compilation to the supported NVIDIA GPU instruction format, register allocation, linkage and input/output mapping, constant upload, validation, and shader caching. The prototype’s fixed-function/flat-color clear path cannot run general OpenGL shaders. Start with a small explicitly advertised shader subset and reject unsupported features cleanly.
5. **Evolve the kernel ABI and miniport scheduling.** Replace the one-operation bounded draw interface with validated resource handles and batched context submissions, GPU virtual-address management, asynchronous fences, queue ownership, and safe job/resource lifetimes. Define reset/error handling and synchronization contracts between user mode and the miniport. Keep validation and ownership in the driver; do not expose arbitrary unchecked user pushbuffers.
6. **Make rendering and presentation GPU-owned.** Render into GPU color/depth surfaces, implement the required resolve/copy path, and connect WGL swap/present to displayable allocations or an efficient copy. Avoid GPU-to-CPU readback for every draw. Add swap interval behavior only after basic correct presentation works.
7. **Keep the whole stack XP-compatible.** Pin a Mesa revision that can be built for Windows XP x64, audit the ICD and dependencies for unsupported imports, CRT calls, synchronization APIs, and compiler-runtime assumptions, and maintain required compatibility shims externally in `../mesa_patches/`. Validate exports, calling conventions, structure sizes, and x64 ABI at every user/kernel boundary.

Suggested staged acceptance gates:

- **G0 — contract:** document supported GPU/OS/Mesa revision, resource model, user/kernel ABI, and the first feature subset.
- **G1 — screen/context:** load a genuine NVX Gallium screen in XP and pass capability/context creation and teardown checks without softpipe callbacks.
- **G2 — resources and synchronization:** allocate/map/upload resources, clear and copy a GPU surface, wait on fences, and verify contents with bounded readback tests.
- **G3 — first GPU draw:** submit vertex buffers and a minimal compiled shader to render a triangle; compare pixels against software reference and confirm the GPU path is used.
- **G4 — useful OpenGL subset:** add depth/stencil, textures/samplers, blending, common primitive types, and state changes required by the target application; add conformance and regression coverage for each advertised capability.
- **G5 — presentation and performance:** present GPU-owned render targets without per-draw readback, run sustained animated workloads, and measure throughput and stalls. Use the 1,000-frame, 30-FPS target above as the initial performance gate.

Every hardware gate should record whether frames actually used the GPU, compare output with a reference, and require no new firmware assertions, MMU faults, or unexpected channel timeouts. Do not advertise a Gallium capability before its behavior is implemented and tested. Exact shader formats, command methods, resource tiling, and XP-compatible Mesa revision still need research and hardware validation before implementation estimates can be reliable.

## Native C797 queue mechanics and requirements before generalizing (November 11, 2026)

Source inspection of `src_driver/nvx_gsp.c:NvxGspSubmitNvc0NativeClear()`
confirms that its successful hardware execution path is tightly scoped: it
holds the global `NvxGrUserSubmitBusy` lock; clears the kernel scratch fence;
constructs a GPFIFO entry over kernel-owned scratch push memory; prepends a
kernel-authored `SET_OBJECT` binding to C797; copies exactly the already
validated 28-dword clear method profile; appends `WAIT_FOR_IDLE` and a
kernel-authored release semaphore; rings the user channel doorbell; and waits
for the exact fence while checking channel/MMU fault state. User data cannot
choose a GPFIFO address, fence address, SET_OBJECT class, or trailing methods.

This helper cannot safely be generalized by replacing its fixed-size copy
with the current batch validator. `Nvx3dValidateNvc0Batch()` only checks packet
framing, BO ownership/relocation metadata and bounds. Before queueing a Mesa
NVC0 stream, the miniport still needs a GPU-method/subchannel allowlist, method
specific payload validation, mandatory relocation checks for every address
method, safe relocation patching against live owned allocations, in-flight BO
pinning through the completion fence, and a context/state policy for multiple
WGL contexts sharing the one kernel-owned GPFIFO. NVC0 screen initialization
also emits SW, M2MF, copy, 2D and 3D object bindings; the current exact clear
path supports only its kernel-owned C797 binding. These requirements are now
the implementation gate for replacing the fixed clear submitter with bounded
submission. Do not wire Mesa's pushbuf kick to this helper until the checks and
buffer lifetimes are enforced in kernel mode.

NullMoth's macOS NVK path uses a different front-end contract: its Metal plugin

Pinned Mesa source audit (`mesa` revision `cc2dcf9abdc6`, November 11, 2026):
NVK's Nouveau memory/device layer calls `DRM_NOUVEAU_GEM_NEW/INFO`,
`DRM_NOUVEAU_VM_BIND`, and `DRM_NOUVEAU_EXEC`, and uses DRM sync objects.

from Gallium to NVK would change the userspace frontend, not eliminate the

copying only its Metal-to-Vulkan bridge would not provide them. Keep the
current WGL/Gallium path unless a separate Vulkan ICD effort is explicitly
chosen; first define the miniport-owned channel, address-space, validated-submit,
and fence APIs required by either Mesa backend.

XP miniport submission audit (November 11, 2026): `IOCTL_NVX_3D_VALIDATE_BATCH`
copies and validates packet framing, session-owned BO references, recognized
NVC0 address pairs, and relocation bounds. It is preflight only: it does not
apply a complete C797 method/subchannel allowlist and does not submit the
user-provided methods. `IOCTL_NVX_3D_SUBMIT` separately accepts a closed set of
fixed clear/triangle operations and rebuilds trusted methods in kernel-owned
scratch memory. This is why neither `DRM_NOUVEAU_CHANNEL_ALLOC` nor
`DRM_NOUVEAU_GEM_PUSHBUF` can be wired to the existing channel or batch escape
yet. The next kernel step must be a separate validated submit request that
checks every method, subchannel, class binding, address range, and BO access,
then copies/rebuilds an approved command stream on the RM-managed channel and
returns a fence. Only after that contract is proven should the DRM wrapper
expose a channel/pushbuf interface to Mesa.
