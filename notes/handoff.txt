# Phase 2C handoff: Windows XP x64 OpenGL on GA104

Updated November 12, 2026 after VFIO run `.100`.

## Current status

The XP x64 Mesa ICD builds and selects `Mesa` / `NV170` (`4.3 Compatibility
Profile`, Mesa 27.0.0-devel). The run creates one native Nouveau Gallium
`pipe_screen` and submits Nouveau pushbuf batches through the NVX channel.
The full VM reaches the OpenGL test and exits, but hardware rendering is not
working: `[MESA_GPU_CUBE_RESULT] FAIL colored_pixels=0` and
`[OPENGL_RESULT] FAIL`. No cube frame has been proven. The status trace reports
`screens=1 callbacks=0`; the native screen is created, while the WGL hybrid
callbacks remain unused.

The current blocker is before render-target readback. The NVC0 miniport batch
at GPFIFO index `0x37` times out, its completion fence remains zero, and the
channel is marked faulted. Later submission requests are rejected. Therefore
black readback is not yet evidence of a separate readback bug. The standalone
native GR triangle path passed in earlier runs, but it does not validate this
Nouveau submission stream.

## Latest hardware evidence

- Full VFIO run: `test_logs/v3.0.0.100-20261112-223346.log`
- Version: `3.0.0.100`; build, XP import/subsystem audit, and guest boot
  completed. OpenGL failed and the script exited nonzero.
- Mesa's test output reports `OpenGL Vendor: Mesa`, `OpenGL Renderer: NV170`,
  and `OpenGL Version: 4.3 (Compatibility Profile) Mesa 27.0.0-devel`.
- The Nouveau trace reports `Native Nouveau Gallium pipe_screen created`,
  `screens=1`, `callbacks=0`, and batches submitted. Cube diagnostic reports
  `gpu_batches=11`, `colored_pixels=0`, `reference_colored=0`.
- At timeout, FIFO entry `0x37` points to push VA `0x18790000`, with 124
  submitted dwords; USERD GET is `0x37`, PUT is `0x38`, and fence `0x237`
  remains zero. The logged descriptor is visible in memory.
- With the corrected PBDMA status register offset (`base + 0x100`), STATUS is
  `0x10011111`. GP_FETCH remains `0x37`; TOP_GET, PB_FETCH, PB_GET, and PB_PUT
  all remain `0x187801CC`. PBDMA interrupts are zero and CHRAM state is
  `0x11C`. Preserve these as raw register evidence; do not infer individual
  STATUS bit meanings without matching the GA104 register documentation.
- The run reports firmware assertion counts reaching 3 after the stalled batch.
  This differs from older successful graphics bring-up runs and should be
  investigated alongside channel fault handling.

## Next work

1. Resolve why GP_FETCH does not consume entry `0x37`, and identify the PBDMA
   fault source. Use the full failed push dump and relevant GA104 PBDMA,
   RAMFC/USERD, channel-switch, and fault registers. The descriptor was visible;
   correlate the stalled push's GPU VA, mapping, channel context, and method
   stream rather than assuming readback is the first failure.
2. Check firmware assertion and CHRAM/PBDMA fault transitions on the first
   failing submission. Avoid treating later rejected submissions as independent
   root causes once the channel is already faulted.
3. Once push submission and its fence complete, separately validate render
   target writes and readback synchronization. Keep a rendered pixel count and
   frame result as the acceptance evidence.
4. Increment the final version component for each real-hardware run. Keep Mesa
   changes outside the Mesa submodule under `mesa_patches/`.
