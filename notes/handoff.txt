# Phase 2C handoff: Windows XP x64 OpenGL on GA104

Updated November 12, 2026 after VFIO run `.103`.

## Current status

The XP x64 Mesa ICD builds and selects Mesa / NV170 (OpenGL 4.3 Compatibility
Profile, Mesa 27.0.0-devel). The run creates a native Nouveau Gallium
`pipe_screen`, allocates its channel and BOs, and submits batches through the
NVX channel. Hardware rendering is still not working: draw probes and the cube
read back black, and `[OPENGL_RESULT] FAIL`. No cube frame has been proven.
The trace reports `screens=1 callbacks=0`; callbacks are the unused WGL hybrid
path and do not represent the native Nouveau screen's activity.

The `.102` run confirms readback is not generally returning zeros:
`[MESA_GPU_CLEAR_BACK_READBACK] pixel=32,64,191` and
`[MESA_GPU_CLEAR_BACK_RESULT] PASS`. But multiple draw probes and the cube
still read black with `GL_NO_ERROR`, including the no-depth cube. This narrows
the immediate issue to draw/raster output or draw-target state; it does not yet
prove the draw commands executed correctly. The earlier `.100` cube readback
also preceded its later submission timeout, so that timeout did not explain
the earlier black frame.

The cube test's former "softpipe reference" was invalid: it changed an
environment variable after creating the GL context, then rendered again
through that same context. That cannot switch an existing Mesa screen from
Nouveau to softpipe. The comparison and environment toggle have been removed.
Cube acceptance now relies on actual colored pixel count, visible color faces,
bounding box, GL error state, and newly submitted GPU batches. The no-depth
check requires at least 2,000 colored pixels and new GPU batches, so two black
frames cannot pass. In both `.101` and `.102`, depth and no-depth cases fail at
0 colored pixels.

## Latest hardware evidence

- Full VFIO log: `test_logs/v3.0.0.102-20261112-230139.log`
- Version `3.0.0.102`: host checks, driver/display build, Mesa ICD build, XP
  import/subsystem audit, and guest boot completed. XP ran the full test and
  shut down normally. The runner exited 1 because hardware OpenGL was not
  proven.
- Mesa reports `OpenGL Vendor: Mesa`, `OpenGL Renderer: NV170`, and
  `OpenGL Version: 4.3 (Compatibility Profile) Mesa 27.0.0-devel`.
- Native Nouveau reports one Gallium screen, device PCI `2488`, chipset `0170`,
  channel allocation success (`c56f0002`), GEM buffer allocation, and GPU batch
  activity. This proves backend setup and submission plumbing, not successful
  rasterization.
- Back-buffer clear readback succeeds with `(32,64,191)`. Full-target draw
  readback, depth probe, cube front/back reads, and no-depth cube all contain
  zero colored pixels with no GL error. The strengthened cube checks fail as
  intended; no actual cube frame is proven.
- The captured Nouveau stream binds render target GPU VA `0x15f40000` with a
  2560-byte pitch, 453 rows, linear layout, and one color target; the other
  swap image is bound at `0x162e0000`. Captured NVC0 streams include constant
  buffer setup and `VERTEX_BEGIN_GL` / `VERTEX_END_GL` packets. So a draw packet
  reaches the submitted stream, though the captures do not yet prove its
  vertex fetch, shaders, or raster writes are valid.
- One captured cube draw begins primitive `QUADS`, sets vertex-array 0 enabled
  with 24-byte stride at GPU VA `0x160903a8`, and submits 24 vertices. Its
  containing GART BO mapping starts at `0x16090000` and spans 2 MiB. This
  narrows the missing output investigation to checking the actual vertex BO
  contents/format, shader code and constant data, and GPU state; the draw is
  not absent from the submitted command stream.
- The `.101` stream exposed a validator inventory gap: Mesa names these
  pointers `VERTEX_ARRAY_START_HIGH/LOW`, but the generator only recognized
  `*_ADDRESS_HIGH/LOW`. The inventory now includes indexed vertex-array
  pointers (32, read access) and the single index-array start pair (read
  access), so Nouveau draw inputs are included in kernel ownership/range
  validation and direct-address reference discovery. A 3D ABI regression test
  covers an owned vertex start address and rejects an out-of-range one. Host
  `make -C src_driver check` passed with the updated table. In `.102`, cube
  push submissions preceding the later timeout were accepted, but pixel output
  did not change; this validation gap was real but was not the cause of the
  black target.
- The log reports that the separate GR pipeline triangle draw, readback, and
  semaphore completed. This miniport probe does not validate Nouveau's draw
  packets or raster output.
- `.102` later hit an NVC0/PBDMA timeout at GPFIFO entry `0x67`: USERD GET
  stayed at `0x67` with PUT `0x68`, fence `0x267` remained zero, and PBDMA
  GET/FETCH stopped at push-buffer VA `0x187801F0`. Firmware assertions rose to 3
  after the timeout. This repeats the `.100` class of failure at a different
  entry; `.101` had completed without a timeout.
- Decoding the `.102` failed 12-dword stream shows five Mesa dwords first:
  `SET_REPORT_SEMAPHORE_A` writes payload `0xc5` to the mapped GART BO at
  `0x11c90000`, followed by `WAIT_FOR_IDLE` and the miniport's completion
  semaphore release to `0x10005000` with payload `0x267`. The Mesa semaphore
  BO is owned and mapped (allocation id 8). This narrows the timeout to this
  synchronization submission sequence or prior PBDMA state; it is not an
  unmapped semaphore address. `.100` and `.102` both show PBDMA
  `PB_HEADER=0x21401b0c` and `PB_COUNT=0` at timeout, with GP_FETCH stalled at
  the current GPFIFO entry. Treat these as repeated raw register values until
  their GA104 semantics are confirmed.
- The animation reports 100 frames at 18.4 FPS, but a black image means this is
  not successful rendered-frame evidence.

## Next work

1. Find why NVC0 submission stops at FIFO `0x67` during the later animation.
   The failed stream is decoded above; trace the Mesa semaphore release and
   miniport completion fence through PBDMA progress, and correlate with the
   first firmware assertion.
2. Extend vertex capture to the cube's actual array address (`0x160903a8`, and
   its adjacent array), then compare the vertex format, shader inputs, code,
   and constants against a known working NVC0/NVK sequence. The `.103` dump is
   from an earlier draw and does not cover the cube input.
3. Separate output stages with progressively smaller Nouveau GPU tests: first
   NVC0 clear, then a minimal supported triangle, then Mesa's shader draw.
   Read the same target after each fence to locate where output disappears.
4. Increment the final version component for every real-hardware run. Keep Mesa
   changes outside the Mesa submodule under `mesa_patches/`.
